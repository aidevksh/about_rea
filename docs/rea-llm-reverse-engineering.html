REA와 LLM은 어떻게 리버스 엔지니어링을 하는가

REA(Reverse Engineer Anything)는 Hopper·Ghidra·IDA 같은 분석 엔진과 브라우저·디버거를 MCP 도구 207개로 묶어 LLM 에이전트에게 건네는 로컬 서버입니다. LLM은 질문을 가설로 쪼개고 다음에 부를 도구를 고릅니다. REA는 엔진을 실제로 돌려 그 결과를 검증 가능한 ‘증거(Evidence)’ 기록으로 돌려줍니다. 이 문서는 그 왕복 과정을 소스 코드 근거와 함께 흐름도로 정리합니다.

분석 기준: github.com/morluto/rea main @ d72d856f5 (2026-10-16) · TypeScript · 파일 4,071개 · 커밋 3,402개 (2026-04-14 첫 커밋: Hopper용 MCP 서버 “betterBinaryMCP”) · 저장소 코드를 빌드하거나 실행하지 않고 소스를 읽어 분석했고, 라인 번호는 이 커밋 기준입니다.

LLM은 엔진이 낸 결과를 읽는다

LLM은 바이너리를 직접 해석하지 않습니다. REA가 Hopper·Ghidra 등에서 뽑아 정규화한 JSON(의사코드, 어셈블리, 호출 관계, 문자열, 참조)을 읽고 다음 질문을 정합니다.

모든 결과는 이름 붙은 증거다

결과는 내용 해시로 ID가 붙은 Evidence로 돌아와 세션 원장에 쌓입니다. LLM은 이 ID로 결론을 인용하고, 같은 분석을 다시 돌리지 않고 필요한 부분만 다시 읽습니다.

모르는 것은 미지로 남긴다

관찰·도출·추론·미지를 구분하는 규칙이 데이터 구조(confidence, authority, coverage, 미지 레지스트리)와 에이전트 스킬 양쪽에 들어 있습니다.

대상의 글은 명령이 아니다

대상에서 나온 문자열·디컴파일 코드는 데이터일 뿐이라는 서버 지침과 결과 표시(_meta.provenance)로 프롬프트 인젝션을 막습니다.

질문 → 계획 → 라우팅

  1. 4

    질문 분해: 무엇을 증명해야 하는지 먼저 정한다

    사용자LLM 에이전트
    • 사용자는 대상과 질문을 줍니다. README의 예시는 “Notes 앱의 검색이 어떻게 동작하는지 증거와 함께 설명하고, 내 프로젝트에 비슷한 기능을 만들어줘”입니다. 대상이 모호하면(“내 앱”) LLM이 먼저 묻고, 예시 앱을 임의로 고르지 않습니다.

03

세션 열기

  1. 6

    open_binary: 대상의 신원을 고정하고 엔진을 하나로 정한다

    LLM 에이전트REA
    • 경로를 realpath로 풀고(앱 번들은 주 실행 파일로), 심볼릭 링크는 거부합니다. 파일 헤더로 형식(Mach-O·ELF·PE·DOS 등)을 판별하고 SHA-256을 스트리밍으로 계산합니다. 읽는 사이 파일이 바뀌면 거부합니다.
    • 심층 분석 후보는 hopper·ghidra·ida·kuna 네 개입니다. provider_id를 주면 그것만 평가합니다. auto면 전부 평가해 쓸 수 있는 후보가 정확히 하나일 때만 바인딩합니다. 둘 이상이면 ‘ambiguous’ 오류로 선택을 요구하고, 실패해도 다른 엔진으로 넘어가지 않습니다(폴백 없음).
    • 이 시점에는 엔진을 띄우지 않습니다. 첫 심층 질의가 들어올 때 기동합니다.

    도구 호출: 개요에서 시작해 좁혀 간다

    LLM 에이전트REA
    • LLM은 binary_overview(세그먼트·함수·문자열 개수), search_strings, list_procedures 같은 작은 개요로 시작해 관심 함수로 좁혀 갑니다.

  3. 9

    Evidence 생성: 정규화하고, 해시로 이름 붙이고, 먼저 기록한다

    REA
    • 결과를 바인딩된 프로필·대상 SHA와 대조하고, 엄격한 스키마(예: functionDossierSchema)로 검증한 뒤 createEvidence로 Evidence를 만듭니다.
    • evidence_id는 ev_ + 의미 필드 전체를 RFC 8785 키 순서로 정규화한 JSON의 SHA-256입니다. 표시 이름과 로컬 경로는 빼므로 같은 관찰은 어디서든 같은 ID가 되고, 가져올 때 다시 계산해 변조된 기록을 거부합니다.
    • 세션 원장(EvidenceLedger)에 먼저 기록합니다. 같은 ID에 같은 내용이면 duplicate, 같은 ID에 다른 내용이면 무결성 오류입니다. 그다음 content(텍스트) + structuredContent(Evidence) + _meta.provenance.untrusted_content: true로 응답합니다.
    • 응답이 전송 한도(기본 약 10 MiB)를 넘으면 resource_constraint와 증거 참조를 돌려줍니다. analyze_function이면 의사코드 첫 페이지를 여는 inspect_analysis_view 호출까지 만들어 줍니다. 분석 자체는 이미 원장에 있습니다.

05

해석 · 후속 질의 루프

  1. 10

    해석: 증거를 읽고 가설을 세운다

    LLM 에이전트
    • LLM은 normalized_result(의사코드, 어셈블리, 호출자·피호출자, 참조, 문자열, 기본 블록, facet_availability)와 함께 confidence·authority·limitations·relationship_coverage를 읽습니다. 커버리지 밖의 것은 ‘없음’이 아니라 ‘미지’로 다룹니다.
    • DX-Ball 사례에서 디컴파일러는 함수를 FUN_00406400(void)로 보여 입력 인자를 놓쳤습니다. LLM은 같은 dossier의 어셈블리 MOV EAX,[EBP+8] → FILD를 보고 정수 인자가 있다고 판단했습니다(06절).
  2. 11

    루프: 남은 질문 하나에 맞춘 도구로 좁혀 간다

    LLM 에이전트REA엔진
    • 확인할 질문이 남아 있으면 그 질문에 맞는 도구를 고릅니다. 호출자를 따라가려면 analyze_function, 상수 값을 확인하려면 read_bytes, 참조 위치는 xrefs, 큰 결과의 일부는 inspect_analysis_view를 씁니다.
    • 같은 엔진 세션과 캐시를 재사용하고, 입력이 바뀌지 않은 같은 호출은 반복하지 않습니다. ‘증거 → 가설 → 좁힌 질의 → 새 증거’로 도는 이 루프가 LLM 리버스 엔지니어링의 중심입니다.

  3. 12

    미지 기록: 풀지 못한 질문을 숨기지 않는다

안전장치와 한계

안전장치

  1. 프롬프트 인젝션 차단. 서버 지침과 결과의 _meta.provenance.untrusted_content 표시로, 대상 문자열 속 “이 명령을 실행하라” 같은 문구를 데이터로만 다루고 사용자에게 보고하게 합니다.
  2. 효과 선언과 클라이언트 승인. 도구마다 10개 효과 플래그(대상 변경, 파일 쓰기, 프로세스 실행, 네트워크, 외부 코드 실행 등)를 선언하고, 여기서 readOnly·destructive·openWorld 힌트를 기계적으로 만듭니다. REA에는 자체 권한 부여 절차가 없고, 승인은 에이전트 클라이언트의 정책이 맡습니다.
  3. 원본은 건드리지 않음. Ghidra는 SHA를 검증한 사본과 임시 프로젝트를 쓰고, IDA는 저장하지 않으며, Hopper 브리지에는 바이트를 쓰는 메서드가 없습니다.
  4. 프로세스 소유권. 모든 자식 프로세스는 소유 프로세스 그룹(Windows는 Job Object)과 실행 토큰으로 묶이고, 정리할 때 토큰을 확인한 뒤에만 신호를 보냅니다.
  5. 설치 안전. 계획 → 승인 → 백업 → 원자적 쓰기 → 재확인·롤백 순서로 진행하고, 무관한 소프트웨어(Node.js, Java, Ghidra 등)는 설치하지 않습니다.
  6. 캡처 마스킹. 인증 헤더·쿠키·저장값·본문 원문은 남기지 않거나 가리고, 선언된 비밀은 [REDACTED:id]로 바꿉니다.
  7. 로컬 실행. 분석은 로컬에서 합니다. 다만 도구 결과(디컴파일 코드 등)는 LLM 제공자에게 전송되므로, 사내 코드나 민감한 대상이라면 제공자의 데이터 정책을 확인해야 합니다.

한계

  1. 의사코드는 원본 소스가 아닙니다. DX-Ball에서도 디컴파일러가 입력 인자와 x87 연산을 빠뜨렸습니다. LLM이 어셈블리로 교차 확인해야 합니다.
  2. 정적 분석은 실행을 증명하지 않습니다. 동적 IPC 채널, 간접 호출, 리플렉션은 미지로 남습니다(Notion 사례의 channel: null).
  3. 커버리지가 없으면 미지입니다. 검색 결과 0건이 기능이 없다는 증거는 아닙니다.
  4. 엔진에 의존합니다. 네이티브 심층 분석에는 Hopper·Ghidra·IDA·Kuna 중 하나가 필요하고, 상용 도구는 정식 라이선스가 있어야 합니다.
  5. 권위와 신뢰도는 생산자가 붙인 라벨입니다. ID 해시는 기록이 바뀌지 않았다는 것만 보장하고, 내용이 참이라는 서명은 아닙니다.
  6. 결론의 품질은 여전히 모델에 달려 있습니다. REA의 평가 문서도 텍스트 휴리스틱이 지어낸 설명을 통과시킬 수 있다고 경고합니다.
